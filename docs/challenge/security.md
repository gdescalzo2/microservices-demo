# Security

Goal: **minimal but real and verifiable** security. Every control has a command that proves it, and residual limits are stated.

## 1. Secrets

| | Implementation | Verification |
|---|---|---|
| No secrets in Git | The Redis password is generated by `create-secrets.sh` (`openssl rand`) directly in the cluster; the script never prints it | CI fails if a rendered manifest contains `kind: Secret` |
| Per-environment separation | Different passwords for `boutique-dev` and `boutique-prod` | `k -n boutique-dev get secret redis-auth -o jsonpath='{.metadata.uid}'` ≠ prod |
| Consumption | Redis reads `REDIS_PASSWORD` from a `secretKeyRef` (`--requirepass`); cartservice reads the whole connection string from a `secretKeyRef` | `k -n boutique-dev describe deploy cartservice` shows the reference, not the value |
| Human access | No team Role includes `secrets` | `rbac-check.sh` → "read secrets: no" |
| Rotation | `create-secrets.sh --rotate` → new value + restart of Redis and cartservice | |

Before this change, upstream Redis had **no authentication**: any pod with network access to port 6379 could read or write carts.

**Residual limits and the production path**
- The Secret is not reconciled by GitOps: if the namespace is recreated, it must be regenerated. In production, use one of:
  - **External Secrets Operator** with Vault or the cloud secret manager: the value stays in the vault, Git holds only the reference;
  - **Sealed Secrets**: the encrypted value lives in Git.
- Secrets in etcd are only base64-encoded: production needs encryption at rest (KMS).
- The password shows up in the `redis-server` process arguments (visible with `ps` *inside* the container). Alternative: a `redis.conf` file mounted from a Secret.
- Redis traffic is not encrypted (no TLS). Acceptable inside the namespace, protected by NetworkPolicies. Production: TLS, or mTLS through a service mesh.

## 2. Workload identity and RBAC

- **One ServiceAccount per service** (upstream), **plus a new one for Redis**, which upstream ran with `default`.
- **`automountServiceAccountToken: false`** on every pod. No service calls the Kubernetes API, so no pod gets a token: a compromised container cannot query the API server.
- **No Role or RoleBinding for workloads**: the ServiceAccounts exist only for identity and audit.

```bash
platform/scripts/rbac-check.sh      # "frontend SA can list pods: no", "token mounted: false"
```

### RBAC for people

| Persona (OIDC group) | dev | prod |
|---|---|---|
| `team-boutique` | `boutique-developer`: read, logs, port-forward, restart, rollback and scale Deployments, delete pods. **No Secrets, no exec** | `boutique-viewer`: read-only, logs. **No Secrets, no exec, no changes** |
| `team-boutique-oncall` | — | viewer + `boutique-oncall`: patch Deployments (restart/rollback), scale, delete pods |
| Argo CD | applies manifests | applies manifests (the only regular change channel in prod) |

Verify with impersonation, no users needed: `kubectl auth can-i patch deployments -n boutique-prod --as alice --as-group team-boutique` → `no`.

In prod the on-call group can act during an incident, but Argo CD self-heal reverts any change that is not in Git. The runbook makes this explicit: `rollback.sh --emergency` suspends auto-sync and reminds you to realign it.

### GitOps guardrails (AppProjects)

- `boutique`: may deploy only to `boutique-dev` and `boutique-prod`. At cluster level it may create only the `Namespace` object: no ClusterRoles, CRDs or webhooks. It cannot manage `ResourceQuota` or `LimitRange`, which belong to the platform team.
- `platform`: only `gateway-infra`, `monitoring` and Kyverno `ClusterPolicy`.
- `boutique-selfservice` (Krateo): only `boutique-*` namespaces.

## 3. Pod security

| Control | Where |
|---|---|
| Non-root (UID 1000), `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `readOnlyRootFilesystem: true` | upstream (checked on every container, init container included) |
| `seccompProfile: RuntimeDefault` | platform patch `pod-hardening.yaml` (missing upstream) |
| **Pod Security Admission `restricted` in enforce** on both namespaces | `overlays/*/namespace.yaml` |
| Explicit image tags (no `:latest`): Kyverno **Enforce** | `disallow-latest-tag`; also `redis:alpine` (mutable tag) → `redis:8-alpine` |
| Mandatory owner label: Kyverno **Enforce** | `require-owner-label` |
| Requests/limits and probes: Kyverno **Audit** | `kubectl get policyreport -A` (expected finding: `loadgenerator` without probes) |

Proof that PSA works:

```bash
kubectl -n boutique-dev run root-test --image=busybox:1.38.0 --restart=Never -- sleep 5
# Error from server (Forbidden): pods "root-test" is forbidden: violates PodSecurity "restricted:latest" ...
```

## 4. Network

- **Default deny** (ingress and egress) in every namespace, plus one NetworkPolicy per service that admits only its real callers. This is the upstream `network-policies` component, previously inactive. Examples: `paymentservice` accepts only `checkoutservice` on port 50051; `redis-cart` only `cartservice`.
- **Single public entry point**: Gateway → `frontend:80`. The `frontend-external` LoadBalancer Service was removed.
- **Metrics not exposed**: port 9090 is on a separate Service that no HTTPRoute references. The smoke test checks this.
- The Gateway accepts HTTPRoutes only from namespaces labelled `platform.example.com/gateway-access=true`.
- **Limit**: egress in the upstream policies is open (`egress: [{}]`), for simplicity and for DNS. In production, restrict it to DNS plus known destinations. kindnet enforces NetworkPolicies since kind v0.24; the `netpol-typo` scenario also demonstrates this.

## 5. Supply chain and CI

- **GitHub Actions pinned to commit SHAs**, not tags. The concrete reason: in March 2026, 76 out of 77 tags of `aquasecurity/trivy-action` were rewritten to ship a credential stealer (CVE-2026-33634). Anyone referencing the tags ran malicious code. The SHAs used here were resolved with `git ls-remote`, not typed from memory (see [ai-usage](ai-usage.md)). Trivy is pinned to v0.69.3, which the advisory lists as safe.
- **Least-privilege CI token**: `contents: read` by default. Only the publishing job gets `packages: write`, and it pushes only from `main`.
- **CI holds no cluster credentials**: Argo CD reads from Git (pull model). A compromised pipeline cannot touch the cluster directly.
- **Image scanning**: Trivy blocks publishing on fixable CRITICAL CVEs; HIGH ones are reported.
- **Frontend image** is distroless (`gcr.io/distroless/static`): no shell, no package manager, minimal attack surface. Operational effect: no `kubectl exec ... sh`, so debugging uses `kubectl debug` with an ephemeral container.

**Residual limits**:
- upstream images are neither scanned nor signed by us (they come from Google's CI registry);
- no signature verification at admission (next step: cosign + a Kyverno `verifyImages` policy);
- no published SBOM.

## 6. Operational risks considered

| Risk | Mitigation |
|---|---|
| Script run against the wrong cluster | The scripts always use `--context kind-boutique` (the `k` function), never the current context |
| Destructive commands | `teardown.sh` and failure scenarios in prod ask for confirmation |
| Kyverno unavailable blocks deploys | Webhook with `failurePolicy: Fail` for Enforce policies (Kyverno default). This is a deliberate fail-closed choice; runbook §2.9 shows how to recognize it |
| Untracked drift in prod | Argo CD self-heal; team RBAC is read-only |
| Rollback that does not return to the expected state | Immutable tags (Enforce policy) + rollback via `git revert` |
